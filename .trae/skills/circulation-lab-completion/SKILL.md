# 三圈环流教具分阶段完成流程

## 使用范围

用于继续完成本项目的规划功能、自动化验证和课堂验收准备。技能保存可复用流程，不保存一次性任务进度、测试输出、个人信息或凭据。每次调用都重新检查工作区和当前实现，不把规划未勾选项直接认定为缺失功能。

用户已授权本项目自动测试全部通过后继续自动提交与非强制推送；后续执行本技能时沿用此授权，除非用户撤销或更改要求。人工闸门仅保留在正式发布或部署前，不因未完成真实课堂、视觉基线或科学审校而阻止开发分支交付。此授权不包括无关文件、强制推送、正式发布或部署。

## 启动检查

1. 检查 `git status --short --branch`，保留用户未提交、未跟踪文件，不擅自删除、重置或覆盖；区分阶段相关改动与无关改动，归属不明确时先确认。
2. 阅读 `docs/superpowers/plans/2026-10-02-three-cell-circulation-platform.md`、相关需求和当前 `package.json`。规划与源码不一致时，以交叉检查结果描述差异，不伪造验收结论。
3. 检查 `src/domain/atmosphere`、`src/state`、`src/features`、`src/App.tsx` 和 `tests`。明确区分已实现、部分实现、未实现、需人工验收四类。
4. 建立任务列表，按阶段拆解。改动前读取周边代码，沿用 React、TypeScript、Zustand、Vitest、Playwright 和现有组件样式。先确认依赖，避免不必要的新依赖。
5. 使用可用的规划与测试驱动开发技能。不要依赖规划文档中提到但当前环境不存在的技能。
6. 检查 `git remote -v` 和当前分支，确认 `origin` 指向本项目仓库，默认推送到 `origin/main`；目标不一致、非 main 分支或待推送历史含无关提交时先确认，不擅自改动远程地址或推送其他提交。

## 阶段一：P0 基础课堂闭环

- 检查自转方向和强度是否从领域参数接通状态操作及控制面板；覆盖方向切换、强度边界、暂停及重置。
- 检查撤销重做是否具备用户入口，边界禁用是否正确，是否恢复相关视图且不混淆因果播放步骤。
- 检查基础预测是否支持预测、实际模拟验证与解释反馈，保持与后续完整诊断任务分离。
- 验证球体、剖面、地图、地点追踪和因果讲解在相同状态下相互一致。
- 运行静态检查、单元测试、构建、相关浏览器流程及离线测试。收集视觉和性能证据。
- 科学审校、批准视觉基线、真实课堂设备和长课稳定性需要人工或真实设备证据；不可用软件渲染短测替代。
- P0 自动测试全部通过后即可执行 Git 交付流程并继续开发；真实课堂设备、视觉基线和科学审校列为正式发布前人工闸门。

## 阶段二：P1 海陆扰动与季风

仅在前阶段闸门明确通过且 Git 交付成功后推进。

- 对照规划检查月份变化、大陆气压异常、海洋热惯性与空间平滑衰减；明确简化模型、参数单位和科学表达边界。
- 先测试冬夏变化、过渡月份、禁用海陆层、强度边界以及多视图投影一致性，再实现缺口。
- 检查东亚与南亚季风模型、场景、探索控件及复合因果解释；不将气压中心单一因素当作完整季风机制。
- 保持已有场景、离线功能和课堂性能约束，新增功能同时增加领域测试和可操作的端到端流程。
- 重走科学、视觉、性能与课堂验收闸门，通过后自动执行阶段 Git 交付流程，再进入 P2。

## 阶段三：P2 学习闭环

仅在前阶段闸门明确通过且 Git 交付成功后推进。

- 对照规划实现学生诊断验证、绘图任务、气候关联和本地学习记录。
- 为诊断规则覆盖正确答案、常见误解、边界输入与反馈解释，避免仅测试模拟实现。
- 学习记录只存必要字段；不采集身份信息，不默认发送远程服务。验证持久化、损坏数据恢复、导出和清除。
- 用端到端测试覆盖预测、操作、验证、解释、记录导出与清除闭环。
- 阶段闸门通过后自动执行阶段 Git 交付流程，核验远程提交后报告最终完成状态。

## 实现纪律

- 每项行为先写最小失败测试，运行并确认预期失败，然后最小实现，再运行相关测试与回归。
- 多代理只用于接口明确且互不编辑相同文件的独立子任务。
- 不额外增加代码注释；不擅自重构无关模块；不创建非必要文档或占位资源。
- 阶段完成后按已授权范围自动提交和非强制推送。发布或部署仍需用户单独授权。绝不使用 `--force`、`--force-with-lease` 或其他覆盖远程历史的方式。

## 验证命令

以当前 `package.json` 为准，在项目根目录执行：

```powershell
npm run check
npm run test:coverage
npm run test:e2e
npm run test:offline
npm run test:visual
npm run test:performance
```

`check` 必须包含 lint、typecheck、单元测试与 build。离线测试独立执行。检查视觉测试是否只采集截图；没有批准基线和实际比对，不得声称视觉回归已通过。软件渲染性能仅作为诊断，不作为真实 GPU 验收。

真实课堂设备上才可启用真实 GPU 性能检查，并在运行后恢复环境变量。长课稳定性按规划要求进行，不用短时采样替代。失败时记录具体原因，先修复再重测，不能把跳过测试算作通过。

## 阶段 Git 交付流程

1. 确认阶段实现和最终自动化验证已通过。待审校、真实设备验证或发布前人工闸门不阻止开发分支提交与推送；部分实现或测试失败时不得触发阶段推送。
2. 检查工作区差异和暂存区，按明确文件路径暂存阶段相关实现、测试与技能改动；不得默认 `git add -A`。排除凭据、个人文件、学习记录、缓存和测试产物。有无关暂存内容或同一文件混合无关改动时先确认，不擅自提交或取消用户暂存。
3. 审查 `git diff --cached` 并运行 `git diff --cached --check`。使用可用的提交技能生成准确的 conventional commit，提交说明包含阶段及改动范围；没有实际改动时不创建空提交。
4. 获取最新远程状态：`git fetch origin main`。失败时停止，不基于过期引用推送。检查 `origin/main..HEAD` 中的全部待推送提交是否均在授权范围内。
5. 使用 `git merge-base --is-ancestor origin/main HEAD` 确认可快进。若历史分叉，停止推送并说明差异，确认保留远程历史的合并方案；不自动变基、重置或覆盖用户改动。经确认合并后必须重新执行验证。
6. 可快进时运行 `git push origin HEAD:refs/heads/main`，不附加强制参数。即使检查后远程又更新，也保留普通推送的拒绝保护，不尝试强推。
7. 推送后使用 `git ls-remote origin refs/heads/main` 核验远程提交，必要时重新 fetch 并确认本阶段提交是远程 main 的祖先，避免把并发新提交误判为丢失。
8. 认证失败时请求支持的授权或请用户完成本机认证，不读取或输出令牌，不将凭据写入技能，不擅自修改全局 Git 配置。分支保护、权限或网络失败时保持阶段 Git 交付未完成，报告具体原因；不得声称推送成功，不推进下一阶段。
9. 交付报告给出阶段、提交哈希、目标分支和远程核验结果。若已在远程包含该阶段提交，不重复提交或推送。

## 阶段交付与暂停规则

完成一项立即更新任务状态。每阶段报告改动文件、执行命令、测试结果、未完成项、发布前人工闸门和 Git 交付状态。自动测试全部通过且远程交付核验完成后，可标记开发阶段完成。

遇到科学审校、基线批准、真实设备验收或需求歧义时，列明所需证据并向用户确认；保持下一阶段待执行，不伪造批准，不自动越过闸门。恢复时重新检查工作区、已有测试与远程状态，不把技能正文当成进度记录。
